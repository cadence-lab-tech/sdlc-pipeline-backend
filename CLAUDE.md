# CLAUDE.md — sdlc-pipeline-backend

Go-сервис SDLC Pipeline: REST для UI, MCP-сервер для локальных агентов, воркер
аренд, индексации репозиториев и детектора дрейфа.

## Прежде чем писать код

Домен описан не здесь, а в [sdlc-pipeline-docs](https://github.com/stepaKaziatko/sdlc-pipeline-docs).
Локально — соседняя директория `../docs/`:

- `../docs/ARCHITECTURE.md` — модель домена, гейты, дрейф, план по фазам
- `../docs/decisions/README.md` — принятые решения
- `../docs/MCP_CONTRACT.md` — контракт агента, если задача касается MCP

Самая точная спецификация домена — `migrations/`. При расхождении с документом
права миграция.

## Стек

Go 1.25 (этой версии требует MCP SDK), Gin, pgx (без ORM), PostgreSQL 17 +
pgvector, эмбеддинги Voyage `voyage-code-3` размерности 1024
([решение 0008](../docs/decisions/0008-voyage-embeddings.md)).
MCP — официальный `github.com/modelcontextprotocol/go-sdk`, схемы артефактов —
`github.com/santhosh-tekuri/jsonschema/v6`. Чтение GitHub и вызовы Voyage — на
стандартной библиотеке: нужны четыре ручки у одного и одна у другого, и
клиентские библиотеки ради них не окупаются.

## Структура

```
cmd/api/            HTTP-сервер: REST и MCP на одних сервисах
cmd/worker/         аренды, индексация, детектор дрейфа, состояние PR
cmd/sdlc/           CLI для агентов и CI
internal/
  config/           настройки из окружения (SDLC_*)
  apperr/           ошибки домена; коды общие для REST и MCP_CONTRACT.md
  domain/           сущности схемы в Go
  workflow/         движок: переходы, прогон гейтов, артефакты, область задачи;
                    agents.go — аренда и сборка контекста этапа,
                    review.go — гейты agent_review и schema_validation,
                    links.go — PR и разрешение дрейфа,
                    drift.go — детектор поверх запросов хранилища,
                    search.go — гибридный поиск,
                    authoring.go — сборка ролей и версий цикла, validate.go —
                    проверка цикла как графа, auth.go — токены и права,
                    bundle.go — перенос связки, webhooks.go — события GitHub,
                    projects.go — каталог репозиториев и документов,
                    metrics.go — метрики цикла
  store/postgres/   запросы поверх pgx, миграции, blobs
  mcp/              MCP-сервер: тулы поверх тех же сервисов
  httpapi/          роутер Gin, middleware (аутентификация, guard прав), хендлеры
  github/           чтение репозиториев: дерево, файлы, PR, проверки
  indexer/          прогон индексации, чанкинг, символы, дельты, состояние PR
  embed/            Voyage и детерминированная заглушка для локального прогона
  testdb/           выделенная база для интеграционных проверок
  blobstore/        вынос крупного содержимого: файловое хранилище за интерфейсом
migrations/         схема и сиды; embed.go встраивает их в бинарник
dev/                docker-compose для локального запуска, e2e.sh
docs/               референсы реализации (не описания решений)
```

MCP-тулы и REST-хендлеры вызывают одни и те же сервисы. Логика не дублируется —
это два транспорта над одним ядром.

## Конвенции кода

- **Хендлеры не содержат логики.** Разобрать запрос, позвать движок или
  хранилище, сериализовать ответ. Иначе MCP-сервер в фазе 2 не сможет встать на
  те же сервисы, не переписывая правила.
- **Методы хранилища принимают `Querier`,** а не работают со скрытым пулом:
  прогон гейтов и перевод задачи обязаны идти одной транзакцией.
- **Переход берёт задачу под `FOR UPDATE`.** Без блокировки два одновременных
  запроса прогонят гейты на одном состоянии и переведут задачу дважды.
- **Ошибки наружу — только `apperr`.** Формулировки драйвера базы клиенту знать
  незачем; `translate()` в `store.go` превращает коды Postgres в коды домена.
- **Гейт в сеть не ходит.** Гейты прогоняются внутри транзакции перехода:
  задача под `FOR UPDATE`, гейты, перевод — одним куском. Сетевой вызов там
  означает блокировку строки задачи на время таймаута чужого API, а `Preview`
  из карточки задачи превратился бы в поток запросов к провайдеру. Всё внешнее
  приносит воркер, гейт читает базу ([решение 0020](../docs/decisions/0020-external-check-reads-snapshot.md)).
- **Новый тип гейта — это evaluator в `internal/workflow/gates.go`** и запись в
  `registerEvaluators()`. Незарегистрированный тип ведёт себя по
  `SDLC_STRICT_GATES`; движок про конкретные статусы по-прежнему не знает.
  Тот же список проверяет `validateWorkflow` при активации цикла — гейт типа,
  которого движок не умеет, всплывает предупреждением, а при `SDLC_STRICT_GATES`
  держит активацию.
- **Движок исполняет цикл, `authoring` его собирает.** Правки цикла не идут
  через `Engine`: там блокировки задач и прогон гейтов, здесь — иммутабельность
  версий. Смешение этих двух ответственностей быстро превращается в правку
  активного цикла из-под работающей задачи.
- **Аренда снимается явно, а не состоянием.** `LeaseHeld` не смотрит на
  `state`: агент, сдавший артефакт, задачу не отпустил. Аренду снимают
  `release`, воркер протухших и уход этапа в `gating`.
- **Побочные эффекты — в `Execute`, не в `Preview`.** Прогон ревьюера заводит
  запрос перехода; `Preview` и `sdlc_check_gates` обязаны оставаться чистой
  проверкой, иначе карточка задачи в UI начнёт запускать агентов при открытии.
- **Права проверяет `workflow.Auth`, а не транспорт.** REST-ручка получает
  уровень через `guard(level)`, MCP-тул зовёт `allow(level)` — оба спрашивают
  один `Auth.Require`. Правило «кому что можно» написано в одном месте, и в
  режиме `header` оно выключено целиком, а не наполовину.
- **Апрув человека ставит человек.** `DecideGate` для `human_approval`
  требует принципала вида `user` в любом режиме: это защита от самоапрува
  агентом, а не от злого умысла.
- **Импорт связки идемпотентен.** Повторный импорт того же не создаёт версий и
  дублей; другая инструкция роли — новая версия, а не правка; цикл приходит
  черновиком. Всё одной транзакцией, `dry_run` — та же транзакция с откатом.
- Комментарии объясняют **почему**, а не что. «Что» видно из кода.

## База данных

```bash
make up        # Postgres + приложение; схема накатывается сама
make logs
make psql
make reset     # снести вместе с данными
```

Postgres на `localhost:55432`, API на `localhost:8088`, база/пользователь/пароль
— `sdlc`. Подробности и переменные окружения — в [dev/README.md](dev/README.md).

Миграции встроены в бинарник (`migrations/embed.go`) и накатываются на старте.
Сиды применяются **только на пустой базе** — они не идемпотентны, пересобрать
демо можно лишь через `make reset`.

### Конвенции миграций

- Нумерация `NNNNNN_name.up.sql` / `.down.sql`, шесть цифр, пара обязательна.
- **Применённая миграция не редактируется.** Изменение схемы — новая миграция.
- Каждая миграция прогоняется на живой базе перед коммитом: up → down → up.
  Ограничения проверяются негативным тестом, а не на глаз.
- Enum'ы — `text` + `CHECK`, не типы Postgres: расширять проще. Down-миграция,
  сужающая `CHECK`, обязана сначала удалить строки отменяемого типа — иначе
  `ADD CONSTRAINT` не пройдёт валидацию на засиженной базе.
- Комментарии в SQL объясняют **почему** поле такое, а не что оно хранит.
- Правка **применённой** миграции ловится не только на ревью: мигратор хранит
  контрольную сумму каждой и отказывается стартовать при расхождении.

### Инварианты схемы

- `workflow_statuses` несёт `UNIQUE (workflow_id, id)` ради композитных FK.
  `tasks (workflow_id, status_id)` ссылается составным ключом — база физически
  не даёт поставить задаче статус из чужого цикла. Не ломать это при рефакторинге.
- Частичные уникальные индексы держат «один активный workflow на проект», «один
  начальный статус», «одна основная роль на статус».
- `task_drift_signals_open_uniq` делает детектор дрейфа идемпотентным.
  Детектор пишется через `ON CONFLICT DO NOTHING`.
- `enforce_task_repo_scope()` — отложенный constraint-триггер. Отложенность
  принципиальна: без неё нельзя одной транзакцией включить `multi_repo` и
  расширить область задачи. Не менять на обычный триггер.
- `workflow_statuses.position` — `DEFERRABLE INITIALLY DEFERRED`;
  переупорядочивание идёт одной транзакцией.
- **Уникальность прогонов разошлась по видам** (`stage_runs_stage_attempt_uniq`
  и `stage_runs_review_attempt_uniq`): перепроверка делит статус с родительским
  этапом. Любой запрос про «текущий этап» обязан фильтровать `kind='stage'` —
  иначе прогон ревью подменит собой этап.
- **`repo_index_runs UNIQUE (repository_id, commit_sha)`** — не только про
  дубли: это защита от параллельной индексации одного коммита. Провалившийся
  прогон поэтому не удаляется, а переоткрывается на новую попытку.
- **`code_files.source_sha`** — sha объекта у провайдера, по которому прогон
  решает, изменился ли файл. Без него инкрементальности нет.
- **`tsvector`-колонки генерируемые**, конфигурация зафиксирована в схеме:
  `simple` для кода, `russian` для артефактов и документов. Смена — миграция.

## Редактирование ролей и цикла

Правило одно, из него следует всё остальное ([решение 0016](../docs/decisions/0016-workflow-versions-immutable.md)):

- **Версия роли иммутабельна.** Правка инструкции — новая строка в
  `role_versions`; `stage_runs.role_version_id` пинит ту, по которой работали.
- **Активный цикл иммутабелен.** Редактируется только `workflows.state='draft'`,
  и активируется целиком. Каждая правка проходит через `Authoring.draft()` —
  других входов в редактирование быть не должно.
- **Задачи доходят по своей версии цикла.** Активация новой версии их не
  трогает: переклеивать `gate_results` на новые гейты — значит терять уже
  вынесенные людьми решения.
- Проверка цикла (`validateWorkflow`) смотрит на него как на граф: начальный и
  терминальный статус, выход из каждого нетерминального, достижимость каждого.
  Схема такие ошибки не ловит — они про цикл целиком, а не про строку.

## Агенты, аренды и перепроверка

Механика — в [решении 0017](../docs/decisions/0017-review-as-nested-stage-run.md),
контракт наружу — в [MCP_CONTRACT.md](../docs/MCP_CONTRACT.md).

- **MCP и REST — два транспорта над одним ядром.** Тул и хендлер зовут один и
  тот же метод `Engine`. Если правило появилось в туле — оно написано не там.
- **MCP-сессии stateless.** Актор приезжает заголовком в каждом запросе;
  сессия с состоянием запомнила бы актора первого запроса и отдавала бы его
  всем последующим. Проект берётся из пути, а не из аргументов тула.
- **Перепроверка — это `stage_run` с `kind='review'`**, живущий внутри
  родительского прогона и принадлежащий гейту. Заводит его `Execute` при
  заблокированном переходе, закрывает — сдача артефакта из `artifact_kind`.
- **Вердикт устаревает от новой сдачи.** `reviewStale` сравнивает время
  артефактов этапа с моментом закрытия ревью. Без этого задача после `fail`
  не прошла бы гейт никогда: ревью не перезапускается, пока результат тот же.
- **Повторная сдача того же `kind` — новая версия.** `SubmitArtifact`
  проставляет `supersedes_id` сам; иначе у задачи оказывается два «актуальных»
  документа одного вида и гейты выбирают из них случайный.

## Индексация, эмбеддинги и поиск

Механика — в [решении 0018](../docs/decisions/0018-incremental-indexing.md) и
[0019](../docs/decisions/0019-hybrid-search.md).

- **Прогон инкрементальный, и это не оптимизация.** Под задачами идёт
  непрерывная кодогенерация: коммиты прилетают пачками, и полная
  переиндексация означала бы платить за весь репозиторий на каждом. Дельта
  считается сравнением листинга дерева с родительским прогоном по
  `code_files.source_sha`; неизменившийся файл копируется вместе с кусками и
  векторами одним SQL. Любая правка индексатора обязана это сохранить —
  проверяется `TestIncrementalRunReusesUnchangedFiles`.
- **Счётчики прогона — не украшение.** `files_reused` против `files_indexed` и
  `chunks_embedded` против `chunks_indexed` — единственный способ заметить, что
  инкрементальность сломалась. Сломанная выглядит как работающая система со
  счётом за эмбеддинги.
- **Кэш эмбеддингов ключуется моделью.** Вектор от другой модели несравним с
  этими: смена модели обязана промахиваться мимо кэша, а не отдавать чужие
  координаты.
- **Недоступная модель прогон не валит.** Куски пишутся без векторов, поиск
  живёт на полнотекстовой половине, векторы досчитывает `BackfillEmbeddings`.
  Детектору дрейфа векторы не нужны вовсе, и останавливать его из-за чужого
  API нельзя.
- **Обрезанный листинг — фатальная ошибка прогона.** Неполный листинг выглядит
  как массовое удаление файлов и завёл бы ложные сигналы дрейфа по всем задачам
  репозитория. Такой прогон валится сразу и без повторов.
- **Поиск по коду ходит только по актуальному прогону ветки.** Прогоны прошлых
  коммитов остаются в базе; без фильтра агент получит несколько версий одного
  файла. Фильтр — `DISTINCT ON (repository_id, branch) ... ORDER BY finished_at DESC`.
- **Полнотекстовый запрос — в OR-семантике** (`sdlc_tsquery`). `websearch_to_tsquery`
  склеивает слова через AND, и фраза из пяти слов не находит ничего, если хоть
  одного слова в куске нет. За релевантность отвечает ранжирование.
- **Векторизация артефактов — в воркере, а не на сдаче.** Агент не должен ждать
  чужой API, чтобы закрыть этап.

## Аутентификация

Механика — в [решении 0021](../docs/decisions/0021-token-auth-and-project-members.md).

- **Два режима.** `SDLC_AUTH_MODE=header` — актор из `X-SDLC-Actor`, права не
  проверяются (отладка цикла, `make up`). `token` — только `Authorization:
  Bearer`, права по `project_members`. Режим по умолчанию выводится из
  `SDLC_ENV`: не-development означает токены.
- **В базе хеш, не токен.** `agent_tokens.token_hash` — sha256; сам токен
  показывается один раз при выдаче. Первый администратор — из
  `SDLC_ADMIN_TOKEN`, upsert по хешу, чтобы рестарт не плодил записи.
- **Токен агента ограничивает, а не расширяет.** Привязка к проекту делает
  токен недействительным вне него даже у администратора; `role_keys` ограничивают
  захват этапов этими ролями (`ClaimOptions.AllowedRoles`).
- **Уровни участия — это не роли специалистов.** `viewer < agent < maintainer <
  admin` про права; `roles` — про поведение агента. Не смешивать.

## Что нельзя делать

- **Хардкодить роли и статусы.** Никаких `if status == "analysis"`. Движок
  работает с переходами и гейтами, поведение роли — данные в `role_versions`.
- **Писать в репозитории пользователя.** Доступ только на чтение
  ([`repositories.access_mode`](migrations/000001_core.up.sql)).
- **Класть секреты в БД.** `repositories.credential_ref` хранит имя секрета во
  внешнем хранилище, не токен.
- **Обходить `principals` в аудите.** Все поля актора — внешние ключи.

## Референсы реализации

`docs/drift_detection.sql` — запросы детектора дрейфа, проверенные на сценарии
из `migrations/seed/drift_demo.sql`. Воркер должен исполнять именно их; при
изменении — перепроверить на том же сценарии.

## Статус

Фазы 1-4 на бэкенде закрыты. Проекты, задачи со свойствами и областью,
артефакты в контент-адресуемых blobs, движок переходов со всеми девятью типами
гейтов, редактор ролей и версий цикла. MCP-сервер с двадцатью четырьмя тулами
и промптом переноса правил, аренды с heartbeat, CLI `sdlc`. Инкрементальная
индексация репозиториев с кэшем эмбеддингов, гибридный поиск, детектор дрейфа
после каждого прогона, синхронизация состояния PR под гейт `external_check`.
Аутентификация по токенам с правами по участию в проекте, перенос правил связкой через REST,
MCP и CLI, вебхуки GitHub, вынос крупного содержимого на диск, метрики цикла,
вычистка старых прогонов индексации.

Сквозной проход задачи по всему циклу проверяется `dev/e2e.sh` — включая
возврат результата ревьюером и повторную перепроверку после доработки.
Инкрементальность, дрейф и поиск — `make test-integration` на выделенной базе.

Не написано: символьный граф через tree-sitter и `code_edges` — требует cgo,
а сборка статическая; объектное хранилище S3 за интерфейсом `blobstore.Store`
(сейчас файловая система).
