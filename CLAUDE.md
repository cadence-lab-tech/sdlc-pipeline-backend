# CLAUDE.md — sdlc-pipeline-backend

Go-сервис Cadence Lab (Clab): REST для UI, MCP-сервер для локальных агентов, воркер
аренд, индексации репозиториев и детектора дрейфа.

## Прежде чем писать код

Домен описан не здесь, а в [sdlc-pipeline-docs](https://github.com/cadence-lab-tech/sdlc-pipeline-docs).
Локально — соседняя директория `../docs/`:

- `../docs/ARCHITECTURE.md` — модель домена, гейты, дрейф, план по фазам
- `../docs/decisions/README.md` — принятые решения
- `../docs/MCP_CONTRACT.md` — контракт агента, если задача касается MCP

Самая точная спецификация домена — `migrations/`. При расхождении с документом
права миграция.

## Стек

Go 1.26 (не ниже 1.25 требует MCP SDK, 1.26 — исправления x/net и
x/crypto), Gin, pgx (без ORM), PostgreSQL 17 + pgvector, эмбеддинги
размерности 1024: Voyage `voyage-code-3` или любой OpenAI-совместимый
эндпоинт, провайдер выбирает инстанс
([решение 0008](../docs/decisions/0008-voyage-embeddings.md)).
MCP — официальный `github.com/modelcontextprotocol/go-sdk`, схемы артефактов —
`github.com/santhosh-tekuri/jsonschema/v6`. Чтение GitHub и вызовы Voyage — на
стандартной библиотеке: нужны четыре ручки у одного и одна у другого, и
клиентские библиотеки ради них не окупаются. Метрики эксплуатации —
`github.com/prometheus/client_golang`: формат exposition, OpenMetrics по
`Accept` и коллекторы рантайма и процесса — это не одна ручка, а формат,
который читает чужой Prometheus.

это два транспорта над одним ядром.

## Конвенции кода

- **Хендлеры не содержат логики.** Разобрать запрос, позвать движок или
  хранилище, сериализовать ответ. Иначе MCP-сервер в фазе 2 не сможет встать на
  те же сервисы, не переписывая правила.
- **Методы хранилища принимают `Querier`,** а не работают со скрытым пулом:
  прогон гейтов и перевод задачи обязаны идти одной транзакцией.
- **Переход берёт задачу под `FOR UPDATE`.** Без блокировки два одновременных
  запроса прогонят гейты на одном состоянии и переведут задачу дважды.
- **Ошибки наружу — только `apperr`.** Формулировки драйвера базы клиенту знать
  незачем; `translate()` в `store.go` превращает коды Postgres в коды домена.
- **Гейт в сеть не ходит.** Гейты прогоняются внутри транзакции перехода:
  задача под `FOR UPDATE`, гейты, перевод — одним куском. Сетевой вызов там
  означает блокировку строки задачи на время таймаута чужого API, а `Preview`
  из карточки задачи превратился бы в поток запросов к провайдеру. Всё внешнее
  приносит воркер, гейт читает базу ([решение 0020](../docs/decisions/0020-external-check-reads-snapshot.md)).
- **Новый тип гейта — это evaluator в `internal/workflow/gates.go`** и запись в
  `registerEvaluators()`. Незарегистрированный тип ведёт себя по
  `SDLC_STRICT_GATES`; движок про конкретные статусы по-прежнему не знает.
  Тот же список проверяет `validateWorkflow` при активации цикла — гейт типа,
  которого движок не умеет, всплывает предупреждением, а при `SDLC_STRICT_GATES`
  держит активацию.
- **Движок исполняет цикл, `authoring` его собирает.** Правки цикла не идут
  через `Engine`: там блокировки задач и прогон гейтов, здесь — иммутабельность
  версий. Смешение этих двух ответственностей быстро превращается в правку
  активного цикла из-под работающей задачи.
- **Аренда снимается явно, а не состоянием.** `LeaseHeld` не смотрит на
  `state`: агент, сдавший артефакт, задачу не отпустил. Аренду снимают
  `release`, воркер протухших и уход этапа в `gating`.
- **Побочные эффекты — в `Execute`, не в `Preview`.** Прогон ревьюера заводит
  запрос перехода; `Preview` и `sdlc_check_gates` обязаны оставаться чистой
  проверкой, иначе карточка задачи в UI начнёт запускать агентов при открытии.
- **Права проверяет `workflow.Auth`, а не транспорт.** REST-ручка получает
  уровень через `guard(level)`, MCP-тул зовёт `allow(level)` — оба спрашивают
  один `Auth.Require`. Правило «кому что можно» написано в одном месте, и в
  режиме `header` оно выключено целиком, а не наполовину.
- **Апрув человека ставит человек.** `DecideGate` для `human_approval`
  требует принципала вида `user` в любом режиме: это защита от самоапрува
  агентом, а не от злого умысла. Токеном задачи апрув не ставится, даже
  если аренду держит человек: движок смотрит на вид токена.
- **`clab server` — порт скриптов пакета, а не новое поведение**
  (решение 0045). Флаги, переменные, имена файлов, отказы и напечатанный
  откат те же, что у `upgrade.sh`, `backup.sh`, `restore.sh` и `lib.sh`
  self-hosted, а `install` — у `get-cadence.sh` и `install.sh` (`.env`
  побайтно по правилу `set_kv`, тест паритета гоняет сам `set_kv`): их
  читают cron клиентов и проверки `ci/` пакета в обоих режимах
  (`CADENCE_DRIVER=clab`). Docker — только через CLI `docker compose` за
  интерфейсом `runner`, тесты — подставным исполнителем без Docker; порты,
  DNS и архитектура для `install` — подставные проверки `serverEnv`. Клиент
  API для `server` не строится (`localCommand`).
- **Импорт связки идемпотентен.** Повторный импорт того же не создаёт версий и
  дублей; другая инструкция роли — новая версия, а не правка; цикл приходит
  черновиком. Всё одной транзакцией, `dry_run` — та же транзакция с откатом.
- Комментарии объясняют **почему**, а не что. «Что» видно из кода.

## База данных

```bash
make up        # Postgres + приложение; схема накатывается сама
make logs
make psql
make reset     # снести вместе с данными
```

Postgres на `localhost:55432`, API на `localhost:8088`, база/пользователь/пароль
— `clab`. Подробности и переменные окружения — в [dev/README.md](dev/README.md).

Миграции встроены в бинарник (`migrations/embed.go`) и накатываются на старте.
Сиды применяются **только на пустой базе** — они не идемпотентны, пересобрать
демо можно лишь через `make reset`.

### Конвенции миграций

- Нумерация `NNNNNN_name.up.sql` / `.down.sql`, шесть цифр, пара обязательна.
- **Применённая миграция не редактируется.** Изменение схемы — новая миграция.
- Каждая миграция прогоняется на живой базе перед коммитом: up → down → up.
  Ограничения проверяются негативным тестом, а не на глаз.
- Enum'ы — `text` + `CHECK`, не типы Postgres: расширять проще. Down-миграция,
  сужающая `CHECK`, обязана сначала удалить строки отменяемого типа — иначе
  `ADD CONSTRAINT` не пройдёт валидацию на засиженной базе.
- Комментарии в SQL объясняют **почему** поле такое, а не что оно хранит.
- Правка **применённой** миграции ловится не только на ревью: мигратор хранит
  контрольную сумму каждой и отказывается стартовать при расхождении.

### Инварианты схемы

- `workflow_statuses` несёт `UNIQUE (workflow_id, id)` ради композитных FK.
  `tasks (workflow_id, status_id)` ссылается составным ключом — база физически
  не даёт поставить задаче статус из чужого цикла. Не ломать это при рефакторинге.
- Частичные уникальные индексы держат «один активный workflow на проект», «один
  начальный статус», «одна основная роль на статус».
- `task_drift_signals_open_uniq` делает детектор дрейфа идемпотентным.
  Детектор пишется через `ON CONFLICT DO NOTHING`.
- `enforce_task_repo_scope()` — отложенный constraint-триггер. Отложенность
  принципиальна: без неё нельзя одной транзакцией включить `multi_repo` и
  расширить область задачи. Не менять на обычный триггер.
- `workflow_statuses.position` — `DEFERRABLE INITIALLY DEFERRED`;
  переупорядочивание идёт одной транзакцией.
- **Уникальность прогонов разошлась по видам** (`stage_runs_stage_attempt_uniq`
  и `stage_runs_review_attempt_uniq`): перепроверка делит статус с родительским
  этапом. Любой запрос про «текущий этап» обязан фильтровать `kind='stage'` —
  иначе прогон ревью подменит собой этап.
- **`repo_index_runs UNIQUE (repository_id, commit_sha)`** — не только про
  дубли: это защита от параллельной индексации одного коммита. Провалившийся
  прогон поэтому не удаляется, а переоткрывается на новую попытку.
- **`code_files.source_sha`** — sha объекта у провайдера, по которому прогон
  решает, изменился ли файл. Без него инкрементальности нет.
- **Один активный цикл на тип задач** держит отложенный constraint-триггер
  `workflows_one_active_per_type`, а не уникальный индекс: типы лежат массивом,
  и пересечение массивов индексом не выражается. Отложенность принципиальна —
  в середине активации активны и старая версия, и новая.
- **`stage_run_usage` без NOT NULL на числах.** Прогон, о котором не
  отчитались, обязан отличаться от прогона за ноль долларов: заполнение
  нулями по умолчанию тихо занизит любую метрику стоимости.
- **`tsvector`-колонки генерируемые**, конфигурация зафиксирована в схеме:
  `simple` для кода, `russian` для артефактов и документов. Смена — миграция.

## Редактирование ролей и цикла

Правило одно, из него следует всё остальное ([решение 0016](../docs/decisions/0016-workflow-versions-immutable.md)):

- **Версия роли иммутабельна.** Правка инструкции — новая строка в
  `role_versions`; `stage_runs.role_version_id` пинит ту, по которой работали.
- **Активный цикл иммутабелен.** Редактируется только `workflows.state='draft'`,
  и активируется целиком. Каждая правка проходит через `Authoring.draft()` —
  других входов в редактирование быть не должно.
- **Задачи доходят по своей версии цикла.** Активация новой версии их не
  трогает: переклеивать `gate_results` на новые гейты — значит терять уже
  вынесенные людьми решения.
- Проверка цикла (`validateWorkflow`) смотрит на него как на граф: начальный и
  терминальный статус, выход из каждого нетерминального, достижимость каждого.
  Схема такие ошибки не ловит — они про цикл целиком, а не про строку.

## Агенты, аренды и перепроверка

Механика — в [решении 0017](../docs/decisions/0017-review-as-nested-stage-run.md),
контракт наружу — в [MCP_CONTRACT.md](../docs/MCP_CONTRACT.md).

- **MCP и REST — два транспорта над одним ядром.** Тул и хендлер зовут один и
  тот же метод `Engine`. Если правило появилось в туле — оно написано не там.
- **MCP-сессии stateless.** Актор приезжает заголовком в каждом запросе;
  сессия с состоянием запомнила бы актора первого запроса и отдавала бы его
  всем последующим. Проект берётся из пути, а не из аргументов тула.
- **Перепроверка — это `stage_run` с `kind='review'`**, живущий внутри
  родительского прогона и принадлежащий гейту. Заводит его `Execute` при
  заблокированном переходе, закрывает — сдача артефакта из `artifact_kind`.
- **Вердикт устаревает от новой сдачи.** `reviewStale` сравнивает время
  артефактов этапа с моментом закрытия ревью. Без этого задача после `fail`
  не прошла бы гейт никогда: ревью не перезапускается, пока результат тот же.
- **Повторная сдача того же `kind` — новая версия.** `SubmitArtifact`
  проставляет `supersedes_id` сам; иначе у задачи оказывается два «актуальных»
  документа одного вида и гейты выбирают из них случайный.

## Оркестрация

Механика — в решениях [0024](../docs/decisions/0024-epic-as-task-with-own-workflow.md),
[0025](../docs/decisions/0025-runner-spawns-subagents.md),
[0026](../docs/decisions/0026-usage-per-stage-run.md).

- **Эпик — задача типа `epic`, а не отдельная сущность.** Своей таблицы у него
  нет: статус, прогоны, артефакты, гейты и лента у эпика те же, что у задачи.
  Любой код, который «знает про эпики», написан не там.
- **Тип задачи — системное свойство `type`,** а набор типов — данные проекта
  (`task_property_defs.enum_values`). Движок знает про тип ровно одно: по нему
  выбирается цикл. Перечень пополняет активация цикла (`DeclareTaskTypes`):
  активный цикл для `epic` означает, что эпик в проекте можно завести. Список
  типов в коде не хардкодится; `domain.DefaultTaskType` — единственная
  константа, и это запасной вариант для задачи без типа.
- **Активных циклов столько, сколько типов, но на тип — ровно один.** Держит
  это отложенный constraint-триггер `enforce_one_active_workflow_per_type()`:
  пересечение массивов частичным уникальным индексом не выражается, а
  активация проходит через состояние, где активны обе версии.
  `RetireActiveWorkflows` уводит на покой только циклы тех же типов — иначе
  активация цикла эпиков оставила бы задачи без цикла.
- **Порядок между задачами — гейт, а не поведение движка.** `blocks` и
  иерархию читает `dependencies_closed`; проекту, которому порядок не нужен,
  гейт ставить незачем. Судит гейт по категории статуса (`done`), а не по его
  ключу: какие статусы завёл проект, движок не знает.
- **Раннер живёт снаружи.** `cmd/clab-runner` запускается там, где есть CLI
  агента и код; бэкенд агентов не поднимает. Захват остаётся pull: оркестратор
  создаёт задачи, раннер их находит, соединения между ними нет. Адрес API
  раннер берёт только из `SDLC_API_URL` и без него не стартует, как `clab`
  без хоста: dev-стек — только явно,
  `SDLC_API_URL=http://localhost:8088/v1 SDLC_PROJECT=SDLC bin/clab-runner`.
- **Агент раннера работает в рабочей копии задачи.** `git worktree` по
  каждому репозиторию области из ответа захвата; клон ищется по `origin` в
  `SDLC_RUNNER_REPOS`, а не по имени каталога. Копия живёт один прогон —
  работу между этапами несёт ветка задачи, поэтому раннер не различает ни
  роли, ни причину захвата. Ветку он находит (`clab/<ключ>-*`), но не
  придумывает, в основном клоне ничего не переключает, а убирает только
  копию, где нечего терять: чистое дерево и `HEAD`, достижимый с `origin`.
- **Квота закрывает новые захваты, а не начатые прогоны** (решение 0027).
  `budgetAllows` стоит в `ClaimWith`: оборванный посреди работы этап стоил бы
  дороже, чем перерасход, который его вызвал. Расход команды — стоимость
  прогонов в проектах, которыми она владеет (`projects.owner_team_id`); в
  проекте, где команда только участвует, платит владелец, иначе один доллар
  считался бы дважды.
- **Стоимость — самоотчёт, и «неизвестно» отличается от нуля.** Числа в
  `stage_run_usage` nullable, прогоны без отчёта считаются отдельно
  (`silent_runs`). Не заполнять их нулями: молчание — это факт, а ноль — цифра.

- **Учётные данные GitHub выбираются по репозиторию, от частного к общему**
  ([решение 0034](../docs/decisions/0034-github-installation-on-tenant.md)):
  секрет репозитория, установка репозитория, установка проекта, секрет
  проекта, токен инстанса. Порядок задан в одном месте —
  `github.CredentialRefs.Resolve`; берётся первый заданный источник, и его
  отказ не повод пробовать следующий. Им же выбирает индексатор
  (`gitHubSource.ForRepository`): цели и прогоны индексации несут установку
  репозитория и установку проекта отдельными полями, без `coalesce`. Тем же
  путём читает PR синхронизация под гейт `external_check` (`SyncRepoRefs`,
  CLAB-84): `RefToSync` несёт те же поля, `PullRequest` и `CheckRuns` зовутся
  только у источника из `ForRepository`, недоступные репозитории
  (`indexTargetLive`) пропускаются, а неудачная попытка пишется в
  `sync_failed_at` и уводит ссылку в конец очереди — нечитаемые PR не
  занимают лимит прохода. Клиента
  по выбранному выдаёт `github.Provider`; движок про транспорт не знает и
  зовёт `GitHubAccess`.
  Проверка доступа отвечает, чем проверяли (`source`), и не подменяет снятую
  или приостановленную установку репозитория учётными данными проекта. Имя
  секрета, которому нет значения в окружении, — ошибка, а не повод молча уйти
  на общий токен: это выдало бы доступ, которого не хотели.
- **Привязка по координатам проверяется тем, чем репозиторий будут читать:**
  своим секретом, подобранной установкой команды или учётными данными
  проекта. Если не объявлено ничего, провайдера не спрашивают: иначе
  заведение проекта зависело бы от доступности GitHub.
- **`app_configured` — «настроено», а не «работает»** (CLAB-79). Он значит
  «задан идентификатор и ключ прочитался на старте». Принимает ли ключ
  провайдер, отвечает поле `app` (`github.AppStatus`: `ok`, `rejected`,
  `unknown`, `not_configured`) — утверждение приложения на `GET /app`.
  Отказ (`rejected`) — 401 после поправки часов и 404: так провайдер
  отвечает на идентификатор приложения, которого у него нет.
  `unknown` — не отказ: недоступный GitHub не выдаётся за отозванный ключ.
  Состояние живёт в памяти процесса api и спрашивается по запросу: кэш на
  пять минут (у `unknown` короче), одна проверка на всех ожидающих, путь «из
  кэша» ждёт провайдера не дольше пяти секунд. В базу оно не пишется, фоновой
  горутины под него нет, публичная `GET /v1/auth/github` его не отдаёт.
  Свежая проверка — только `GET /projects/{key}/github/check`.
- **Сводка проекта (`GET /projects/{key}/health`) только читает:** кэш
  состояния приложения и счётчик из базы. Её зовёт оболочка интерфейса на
  каждой странице проекта, от всех участников сразу (уровень `viewer`), и
  сама она к провайдеру на каждый запрос не ходит — вешать на неё новую
  проверку «при открытии страницы» нельзя. Текста провайдера и расхождения
  часов в ней нет: подробности видят те же, кто видел настройки.
- **Сигнал «репозиторий не читается» пишет воркер, читает api.** Провал
  чтения головы ветки прогона не заводит, поэтому след — в
  `repository_head_failures` (серия по ветке, `Indexer.Enqueue`); провал
  прогона виден по самому прогону. Правило `failure` одно на строку
  `GET /projects/{key}/index` и на счётчик сводки — фрагменты
  `indexFailureSource` и `indexHealthFrom` в `store/postgres/index.go`:
  прогон в `failed`, прогон в очереди после второй неудачной попытки или
  голова, не прочитанная на двух проходах подряд. Класс ошибки не
  фильтруется и по тексту не узнаётся; репозиторий вне целей индексации
  сигнала не несёт.

## Индексация, эмбеддинги и поиск

Механика — в [решении 0018](../docs/decisions/0018-incremental-indexing.md) и
[0019](../docs/decisions/0019-hybrid-search.md).

- **Прогон инкрементальный, и это не оптимизация.** Под задачами идёт
  непрерывная кодогенерация: коммиты прилетают пачками, и полная
  переиндексация означала бы платить за весь репозиторий на каждом. Дельта
  считается сравнением листинга дерева с родительским прогоном по
  `code_files.source_sha`; неизменившийся файл копируется вместе с кусками и
  векторами одним SQL. Любая правка индексатора обязана это сохранить —
  проверяется `TestIncrementalRunReusesUnchangedFiles`.
- **Счётчики прогона — не украшение.** `files_reused` против `files_indexed` и
  `chunks_embedded` против `chunks_indexed` — единственный способ заметить, что
  инкрементальность сломалась. Сломанная выглядит как работающая система со
  счётом за эмбеддинги.
- **Кэш эмбеддингов ключуется моделью.** Вектор от другой модели несравним с
  этими: смена модели обязана промахиваться мимо кэша, а не отдавать чужие
  координаты.
- **Недоступная модель прогон не валит.** Куски пишутся без векторов, поиск
  живёт на полнотекстовой половине, векторы досчитывает `RefreshEmbeddings`.
  Детектору дрейфа векторы не нужны вовсе, и останавливать его из-за чужого
  API нельзя.
- **Векторный поиск — только по векторам текущей модели.** Каждый векторный
  запрос фильтрует `embedding_model`; куски другой модели пересчитывает тот же
  проход воркера, а инкрементальный прогон их векторы не наследует. Новое
  место, где пишется или читается вектор, обязано знать модель.
- **Обрезанный листинг — фатальная ошибка прогона.** Неполный листинг выглядит
  как массовое удаление файлов и завёл бы ложные сигналы дрейфа по всем задачам
  репозитория. Такой прогон валится сразу и без повторов.
- **Поиск по коду ходит только по актуальному прогону ветки.** Прогоны прошлых
  коммитов остаются в базе; без фильтра агент получит несколько версий одного
  файла. Фильтр — `DISTINCT ON (repository_id, branch) ... ORDER BY finished_at DESC`.
- **Полнотекстовый запрос — в OR-семантике** (`sdlc_tsquery`). `websearch_to_tsquery`
  склеивает слова через AND, и фраза из пяти слов не находит ничего, если хоть
  одного слова в куске нет. За релевантность отвечает ранжирование.
- **Векторизация артефактов — в воркере, а не на сдаче.** Агент не должен ждать
  чужой API, чтобы закрыть этап.

## Аутентификация

Механика — в [решении 0021](../docs/decisions/0021-token-auth-and-project-members.md).

- **Два режима.** `SDLC_AUTH_MODE=header` — актор из `X-SDLC-Actor`, права не
  проверяются (отладка цикла, `make up`). `token` — только `Authorization:
  Bearer`, права по `project_members`. Режим по умолчанию выводится из
  `SDLC_ENV`: не-development означает токены.
- **Вход через провайдера не заводит второй транспорт.** Фронтенд проходит
  authorization code flow с PKCE и приносит ID-токен, бэкенд его проверяет
  (`internal/oidc`) и выдаёт обычный токен `agent_tokens` с
  `kind='session'` и коротким сроком. Ни cookie, ни JWT в заголовке: вторая
  ветка в `Auth` — это второй набор ошибок в правах.
- **Принципал ключуется `sub`, и только им.** Почту и имя в IdP меняют; по
  хэндлу вход ни к кому не привязывается ([решение 0033](../docs/decisions/0033-tenant-is-team.md)):
  на открытом инстансе принципал под чужим логином достался бы тому, кто
  первым с ним войдёт, включая администратора бутстрапа. Занятый хэндл
  получает суффикс.
- **Человек по хэндлу не заводится.** `findPrincipal` ищет `user` среди
  существующих и заводит на месте только `agent`; `ResolveActor` остаётся
  для актора заголовка, бутстрапа и воркера.
- **Состав команды синхронизирует провайдер, роль — человек.** Вход добавляет
  и снимает участие в командах с настроенным `team_idp_groups`; лид не
  понижается и не выводится, а команды без сопоставления групп не трогаются
  вовсе.
- **В базе хеш, не токен.** `agent_tokens.token_hash` — sha256; сам токен
  показывается один раз при выдаче. Первый администратор — из
  `SDLC_ADMIN_TOKEN`, upsert по хешу, чтобы рестарт не плодил записи.
- **Токен агента ограничивает, а не расширяет.** Привязка к проекту делает
  токен недействительным вне него даже у администратора; `role_keys` токена
  сужают захват этапов до этих ролей.
- **Токен задачи — учётные данные исполнителя этапа** ([решение 0049](../docs/decisions/0049-stage-executor-credentials.md)).
  `agent_tokens.kind = 'task'` со ссылкой на `stage_runs`; выпускает держатель
  живой аренды (`Auth.IssueTaskToken`, `POST /tasks/{key}/task-token`,
  `clab token task`). Жизнь — аренда: `TokenByHash` сверяет прогон на каждом
  запросе, `RevokeRunTokens` гасит токены в транзакции события аренды
  (release, протухание, повторный захват, `gating`, `FinishStageRun`).
  Рамки — `workflow/tasktoken.go`: запись в свою задачу и свой прогон
  (`RequireOwnTask`, `OwnRun`), чтение в круге задачи (`RequireReadable`,
  `TaskReadCircle`), сводка списков, поиск по области (`SearchBound`).
  REST зовёт их из `guard` и ручек записи, MCP — из `inProject`,
  `ownTarget`, `leaseTarget`. Только в режиме `token` и только для токена
  задачи: личный токен и сессия этих проверок не видят.
- **Токену задачи — белый список, по умолчанию отказ** (CLAB-208).
  Перечень тулов, промптов и маршрутов — `workflow/executor.go`
  (`ExecutorMay`); его зовут обёртка `add`/`addPrompt` в MCP и слой
  `executorOnly` на группе `/v1` — до уровня и `is_admin`. Новый тул или
  ручка исполнителю закрыты, пока их не внесли в перечень; тесты сверяют
  перечень с зарегистрированными тулами и `gin.Engine.Routes()`. Внутри
  разрешённого: запись — своя задача и её дети (`RequireWriteCircle`,
  `RequireLink`), гейт — только `passed` по чек-листу своего этапа
  (`DecideGate` с привязкой), переход — `advance` и `reject`
  (`ExecuteBound`). Транспорты передают `Auth.Bound`, а не зовут `Execute`.
- **Роли специалистов выдаёт участие, токен их только сужает**
  ([решение 0030](../docs/decisions/0030-member-roles-github-login-open-projects.md)).
  `project_members.role_keys` и `project_teams.role_keys` ставит администратор
  проекта; `Auth.AllowedRoles` пересекает их с ролями токена и отдаёт
  `ClaimOptions.AllowedRoles`. NULL — любые роли, пустой список — ни одной:
  та же договорённость, что у токена. Считать рамки из одного токена, как в
  фазе 4, нельзя — токен участник выдаёт себе сам.
- **Вход через GitHub — тот же путь, что через OIDC.** Код авторизации меняет
  бэкенд (`github.OAuth`, секрет клиента в окружении), принципал ключуется
  `github:<id>` в том же `idp_subject`, сессия та же. Токен пользователя живёт
  в запросе и не сохраняется: репозитории читает установка приложения.
- **Установка приложения принадлежит команде** ([решение 0034](../docs/decisions/0034-github-installation-on-tenant.md)).
  `github_installations` записывается только через `Auth.ConnectGitHub`:
  право на установку доказывает `GET /user/installations` токеном
  пользователя из кода повторной авторизации — номер установки не
  доказательство. Тем же токеном читается пересечение репозиториев с личным
  доступом; токен не сохраняется. Репозиторий помнит установку, цели
  индексации и вебхуки берут `coalesce(r.installation_id,
  p.github_installation_id)`; доставка без установки не обслуживается.
  Снятая или приостановленная установка и убранный из неё репозиторий
  выпадают из целей и очереди (`indexTargetLive`), индекс не удаляется.
- **Проект всегда принадлежит команде** ([решение 0033](../docs/decisions/0033-tenant-is-team.md)).
  Без явной команды `OwnerTeamFor` отдаёт личную команду создателя
  (`ensurePersonalTeam` заводит её при входе, бутстрапе и первом проекте);
  при `SDLC_PROJECT_CREATION=open` ей не нужно право на проекты, при
  `teams` его выдаёт администратор. `teams.kind`: личная команда участников
  не принимает, организацию заводит любой человек.
- **`SDLC_TENANCY=single` — профиль, а не другая модель** (CLAB-88). Все
  ветвления читают `Auth.single()` в `workflow/tenants.go`. Личная команда
  не заводится ни при входе и бутстрапе (`personalTeamAtLogin`), ни лениво
  (`ensurePersonalTeam` отвечает «не найдена»); `OwnerTeamFor` без команды —
  400 для всех, оставшаяся с `shared` личная команда не подставляется;
  `Me.can_create_projects` не учитывает `SDLC_PROJECT_CREATION=open` для
  человека без команды. Команды заводит и превращает в организации только
  администратор инстанса; `SDLC_PROJECT_CREATION` решает лишь, получает ли
  его команда право на проекты сразу. Тарифов нет: `ListPlans`,
  `SetTeamPlan`, `TeamPlan` — 404, `TeamDetail.plan` в ответе нет. Схема
  `plans`/`subscriptions` та же.
- **Квота — слой рядом с правами, не условие в домене.** `memberQuota` в
  `SetTeamMember` читает `PlanOf` (активная подписка, иначе `free`) и
  считает состав; при `SDLC_TENANCY=single` отвечает «можно», не спрашивая
  базу. Движок и индексатор про тарифы не знают.
- **Уровни участия — это не роли специалистов.** `viewer < agent < maintainer <
  admin` про права; `roles` — про поведение агента. Не смешивать.
- **Действующий уровень — максимум из путей, а не последний назначенный.**
  Прямое участие (`project_members`), участие команды (`project_teams` через
  `team_members`) и лид команды-владельца складываются в один уровень
  ([решение 0027](../docs/decisions/0027-teams-and-oidc.md)). Считает его
  `EffectiveRole` одним запросом: проверка прав идёт на каждый запрос, и два
  похода в базу здесь стоят дороже, чем выглядят. Отдельно спрашивать
  `MemberRole` в проверках прав нельзя — это половина правила.
- **Правило уровня исполняет движок, а не ручка.** «Агент заводит только детей
  задачи, которую держит» живёт в `agentMayCreate`, а транспорт лишь передаёт
  уровень (`Auth.Level`). В режиме `header` уровень максимальный: права
  выключены целиком, и это касается и этого правила.
- **Приглашение — отложенное добавление участника**
  ([решение 0035](../docs/decisions/0035-invites-by-link.md)). Права на выдачу
  те же, что у `SetTeamMember` (лид) и `SetMember` (администратор проекта),
  плюс уровень не выше действующего у выдающего; выдаёт и принимает только
  человек, в любом режиме. Токен `clab_inv_…` показывается один раз, в
  `invites` лежит sha256; в API он ходит в теле (`/invites/lookup`,
  `/invites/accept`), а не в пути — пути оседают в логах. Статус не
  хранится: `Invite.StatusAt` считает его из времён, колонка разошлась бы
  со сроком. Квота — на приёме, а не на выдаче: протухшие ссылки не держат
  места. Приём — одна транзакция: приглашение `FOR UPDATE OF i`, команда
  `FOR UPDATE` до `memberQuota` (иначе два приёма разных ссылок на последнее
  место прошли бы оба), участие с `added_by` выдавшего. Уже участник
  ничего не меняет: смена уровня — прямое действие администратора.

## Хранилище содержимого и реплики

- **Хранилище выбирается одним местом — `blobstore.Open`.** И api, и воркер
  зовут её, и заданный бакет (`SDLC_BLOB_S3_BUCKET`) перекрывает каталог
  (`SDLC_BLOB_DIR`): каталог прописан в образе по умолчанию, а бакет — решение
  человека. Разъехаться api и воркеру нельзя: воркер читает при векторизации
  то, что вынес api.
- **Пределы содержимого сверяются на старте.** `SDLC_BLOB_INLINE_MAX_BYTES`
  не больше `SDLC_BLOB_MAX_BYTES` и не больше `blobstore.InlineMaxBytes`
  (4 МиБ) — иначе `config.Load` падает, с хранилищем и без. `PutBlob`
  держит то же правило для вызовов в обход конфигурации: общий предел — на
  любом пути, inline тоже, порог inline срезается до 4 МиБ. Пределы api и
  воркер передают в хранилище и без внешнего хранилища.
  `SDLC_INDEX_MAX_FILE_BYTES` сверяется с ними там же (CLAB-82): не больше
  `SDLC_BLOB_MAX_BYTES`, а без внешнего хранилища — не больше 4 МиБ, иначе
  старт падает и при выключенной индексации. Индексатор держит охрану:
  файл крупнее `Store.BlobLimit()` пропускается с `warn`, как файл крупнее
  своего предела, а не роняет прогон на `PutBlob`.
- **Подпись S3 считается на стандартной библиотеке.** SigV4 — пара хэшей, а
  запросов всего три (PUT, GET, HEAD); клиентская библиотека ради них в
  зависимости не идёт — то же правило, что и для GitHub.
- **Чужой адрес отбивается, а не читается наугад.** `s3://` из другого бакета
  и `file://` в S3-хранилище — ошибка: адрес мог остаться от прежней
  установки, и молча отдать пустоту хуже, чем отказать.
- **Метрики эксплуатации — `internal/metrics`, отдельный порт** (CLAB-126).
  `SDLC_METRICS_ADDR` пуст по умолчанию; задан — api и воркер поднимают
  слушатель только с `/metrics`, синхронно (занятый порт роняет старт). На
  основной роутер `/metrics` не вешается: он смотрит в интернет. Реестр
  свой у каждого процесса, не глобальный. **Ни одной метки с данными
  проекта**: ни ключей проектов и задач, ни репозиториев, хэндлов,
  токенов, `request_id` — маршрут идёт шаблоном `c.FullPath()`, мимо
  маршрутов — `unmatched`, метод — из закрытого набора, код — классом.
  **Состояние базы считает только воркер** (`postgres.OpsState`, на тике
  аренд, не на scrape): реплики api задвоили бы очередь. Задания воркера
  идут через `metrics.Worker.Job` — длительность, ошибки, метка успеха по
  имени задания; имена — значения метки `job`, их читают правила
  оповещения в `docs/admin.md` пакета, и меняются они только вместе. Все
  методы nil-безопасны: без адреса метрик код заданий тот же.
- **Реплик api может быть сколько угодно, воркер один.** В процессе api ничего
  не живёт: миграции берут advisory-блокировку (`postgres.Migrate`), MCP
  работает без сессий, фоновые проходы вынесены в воркер. Всё, что кэшируется
  в памяти (JWKS, токены установки GitHub), у каждой реплики своё и сходится
  само. Ставить в api фоновую горутину с расписанием нельзя — её погонит
  каждая реплика.

## Что нельзя делать

- **Хардкодить роли и статусы.** Никаких `if status == "analysis"`. Движок
  работает с переходами и гейтами, поведение роли — данные в `role_versions`.
- **Писать в репозитории пользователя.** Доступ только на чтение
  ([`repositories.access_mode`](migrations/000001_core.up.sql)).
- **Класть секреты в БД.** `repositories.credential_ref` и
  `projects.github_credential_ref` хранят имя секрета, не токен;
  `projects.github_installation_id` — идентификатор установки приложения, а
  токен по ней выписывается на час и живёт в памяти процесса
  ([решение 0028](../docs/decisions/0028-github-app-per-project.md)).
- **Обходить `principals` в аудите.** Все поля актора — внешние ключи.

## Верстак задачи

Файлы задачи правятся в рабочей копии `.worktrees/<ключ>/backend` на хосте,
а собираются и проверяются в верстаке её стека — контейнере
`golang:1.26-bookworm` с примонтированной копией
([решение 0041](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0041-task-toolbox-in-compose.md)).
Порядок целиком — `../docs/PROCESS.md`, раздел «Верстак задачи»; устройство —
`dev/README.md`, «Верстаки задачи».

- Стек из копии задачи: `dev/stack.sh up <ключ>`. Поднят оркестратором или
  соседней ролью — повторный `up` безвреден.
- Сборка и модульные тесты: `dev/stack.sh exec <ключ> backend go build ./...`,
  так же `go vet ./...`, `go test ./...`, `make lint` (`go vet` и
  `gofmt -l`; неформатированный файл роняет цель с перечнем — исправить
  `gofmt -w <файл>`).
- Интеграционные тесты: `dev/stack.sh exec <ключ> backend make test-integration`
  — в `sdlc_test` Postgres этого стека, соседям не мешают.
- Внутри верстака нет Docker и не работает git: `make up`, `dev/e2e.sh`,
  `dev/e2e-orchestration.sh`, коммиты и push — на хосте. Стек пересобирает
  api по коду копии при каждом `up`.
- Новая миграция: номер сверять со свежим `main` и с ветками соседей —
  `git worktree list` здесь покажет, какие задачи правят бэкенд на этой
  машине, `git diff --stat origin/main...<ветка соседа>` — трогают ли они
  `migrations/`.

## Референсы реализации

`docs/drift_detection.sql` — запросы детектора дрейфа, проверенные на сценарии
из `migrations/seed/drift_demo.sql`. Воркер должен исполнять именно их; при
изменении — перепроверить на том же сценарии.

## Статус

Фазы 1-5 на бэкенде закрыты. Проекты, задачи со свойствами и областью,
артефакты в контент-адресуемых blobs, движок переходов со всеми девятью типами
гейтов, редактор ролей и версий цикла. MCP-сервер с двадцатью восемью тулами
и промптами переноса правил и работы над задачей, аренды с heartbeat,
CLI `clab`. Инкрементальная
индексация репозиториев с кэшем эмбеддингов, гибридный поиск, детектор дрейфа
после каждого прогона, синхронизация состояния PR под гейт `external_check`.
Аутентификация по токенам с правами по участию в проекте, перенос правил связкой через REST,
MCP и CLI, вебхуки GitHub, вынос крупного содержимого на диск, метрики цикла,
вычистка старых прогонов индексации.

Оркестрация (фаза 5): эпик — задача типа `epic` на своём цикле, иерархия
задач, десятый гейт `dependencies_closed`, тулы `sdlc_create_task`,
`sdlc_link_tasks`, `sdlc_assign_task`, `sdlc_report_usage` и промпт
`work_on_task`, адресное назначение, учёт стоимости прогонов с разрезом в
метриках, раннер саб-агентов `cmd/clab-runner`.

Фаза 7, CLI как `gh` ([решение 0032](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0032-cli-login-device-flow.md)):
`clab auth login` — device flow поверх интерфейса (`cli_login_requests`,
`POST /v1/auth/cli`, страница `/login/cli`), конфиг `~/.config/clab` по
хостам, проект по `origin` через `GET /v1/projects?repo=`, `clab mcp
install`, таблицы для команд чтения и `--json`, релизы `release.yml`;
раздача — публичный тап `cadence-lab-tech/homebrew-tap` ([решение 0038](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0038-public-cli-distribution.md)):
`release.yml` выкладывает архивы релизом туда и шлёт `repository_dispatch` с
тегом и суммами, формулу и `install.sh` держит сам тап, качают без токена.
Тот же тег собирает образ версии `sdlc-pipeline-backend:vX.Y.Z` (задание
`image`: `VERSION` из тега, `/LICENSE` внутри, без `LICENSE` в корне выпуск
падает до сборки); frontend по тому же тегу — свой образ. Тот выпуск, что
опубликовал образ вторым, шлёт `cadence-release` с `client_payload.version`
в `cadence-lab-tech/self-hosted` (`.github/release/notify-self-hosted.sh`,
одинаковый в обоих репозиториях, секрет `SELF_HOSTED_DISPATCH_TOKEN`).
С v0.9.0 образ несёт SBOM и provenance BuildKit, digest индекса подписан
cosign без ключей, к нему приложен VEX (`.github/release/openvex.json`), а
`checksums.txt` CLI — бандл подписи; событие несёт образы по digest и уходит,
когда подписаны оба ([решение 0046](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0046-supply-chain-signatures-pins.md)).
Порядок выпуска и что делать с половиной — раздел «Выпуск версии» в
README.

Фаза 8, арендатор ([решение 0033](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0033-tenant-is-team.md)):
`teams.kind`, личная команда при входе, обязательный `owner_team_id`,
организация для любого вошедшего, `plans`/`subscriptions` с пределом
участников на `free`, `POST /teams/{key}/convert`, `PUT /teams/{key}/plan`,
`SDLC_TENANCY`, человек по хэндлу не заводится.
GitHub по кнопке ([решение 0034](https://github.com/cadence-lab-tech/sdlc-pipeline-docs/blob/main/decisions/0034-github-installation-on-tenant.md)):
`github_installations` на команде, `POST /teams/{key}/github/connect` по
коду повторной авторизации, `POST /projects/{key}/github/repositories`
пачкой, `repositories.installation_id`, маршрутизация вебхуков по
установке, события `installation` и `installation_repositories`,
`SDLC_GITHUB_APP_SLUG`.
Приглашения ссылкой (решение 0035): `invites` с одной целью и вычисляемым
статусом, `POST/GET /teams/{key}/invites`, `POST/GET /projects/{key}/invites`,
`DELETE /invites/{id}`, `POST /invites/lookup` и `/invites/accept` с токеном
в теле, приём под блокировкой приглашения и команды. CLI — `clab invite
create / list / revoke`: ссылка от адреса хоста печатается один раз, правил
CLI не знает.

Сквозной проход задачи по всему циклу проверяется `dev/e2e.sh` — включая
возврат результата ревьюером и повторную перепроверку после доработки. Задачу
он заводит себе сам и повторяется на той же базе; `TASK=<ключ>` берёт
существующую на `new` с backend в области и без frontend. Проход
эпика — `dev/e2e-orchestration.sh`: нарезка, назначение, стоимость, гейт
зависимостей; эпик он тоже заводит себе сам, `EPIC=<ключ>` берёт
существующий на `planning` без дочерних задач. Инкрементальность, дрейф,
поиск и оркестрация — `make test-integration` на выделенной базе; в
верстаке стека задачи
(`dev/stack.sh exec <ключ> backend make test-integration`) — в базе этого
стека, на хосте — `dev/stack.sh test-db` находит её сам (`KEY=` для явного
выбора).

Деплой (решение 0031): `devops/terraform` (локальная папка владельца, вне
репозитория) описывает машину, IPv4, файрвол, A-запись и бакет; `deploy/` —
стек за Caddy и выкладку по короткому SHA из GHCR;
`.github/workflows/deploy.yml` собирает образ и выкладывает его. Правила
работы с продом — `devops/CLAUDE.md` в той же локальной папке.

Не написано: символьный граф через tree-sitter и `code_edges` — требует cgo,
а сборка статическая.
